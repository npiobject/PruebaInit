PruebaInit · guía

El método «PC arranca, móvil continúa», entero. Para el arranque rápido de un proyecto nuevo, ARRANQUE.md.

La idea

El repositorio es la única fuente de verdad: código, planificación y decisiones. El trabajo se hace en sesiones de claude.ai/code con el repo seleccionado, desde el móvil o desde la web, con el PC apagado. El PC solo sirve para bajar una copia de lectura cuando hace falta.

De ahí salen tres reglas que gobiernan todo lo demás:

  • Nada se edita fuera del repo. Ni en Drive, ni en la copia local. Si algo difiere, gana el repo.
  • Nada se verifica desde la sesión. El sandbox no tiene salida a internet: quien comprueba un despliegue es el propio workflow, que sí la tiene.
  • El camino es siempre nube → PC. Nunca al revés.

Un proyecto nuevo arranca solo con lo obligatorio. Fly y Drive se activan a mitad de proyecto sin rehacer nada.

Ciclo de una sesión

  1. Abres claude.ai/code con el repo seleccionado y describes lo que quieres.
  2. El agente lee CLAUDE.md (reglas del proyecto) y trabaja en una rama.
  3. Push a main → los workflows despliegan y verifican.
  4. El agente consulta la API de GitHub Actions y no avisa hasta que el run del SHA está en success.
  5. Cierre: resumen de 5 líneas en docs/planificacion/sesiones/AAAAMMDD-HHMM.md, y copia a Drive si está configurado.

docs/planificacion/ es la carpeta de este proyecto y en un repo generado arranca vacía; el historial de la plantilla queda apartado en docs/plantilla/, como referencia de solo lectura. pages.yml solo se puede verificar en main: el entorno github-pages únicamente despliega desde la rama por defecto.

Un aviso de «ya puedes probarlo» sin SHA, URL y número de build no vale. Es la única señal de que la verificación se hizo de verdad.

Pages

pages.yml publica el contenido de docs/ en cada push a main. El único paso manual de todo el método es cambiar, una vez por repo, Settings → Pages → Source de «Deploy from a branch» a «GitHub Actions». Si se deja como viene, el enlace funciona pero sirve el README en vez del mock.

docs/index.html es el mock vivo; los anteriores se archivan en docs/mocks/NNN-nombre.html. Cada uno lleva <meta name="build"> con un número nuevo, que es lo que se cita al avisar. El sitio es público: ahí no van claves, endpoints internos ni datos reales.

Fly (opcional)

deploy.yml mira primero si existe el secreto FLY_API_TOKEN. Si no existe, termina en verde con el aviso «Fly no configurado» y no despliega nada; el repo no se queda con un check rojo permanente por una pieza que no usas.

Nombre de la app

Sale de la variable de repositorio FLY_APP si existe. Si no, se deriva: <repo>-<owner> en minúsculas, saneado a [a-z0-9-] y recortado a 30 caracteres. app/fly.toml ya no lleva clave app: el nombre se pasa con --app en el despliegue, así que la plantilla no arrastra el nombre de otro proyecto.

Verificación

El backend expone GET /salud con {"ok":true,"build":"<SHA>"}, donde el SHA lo inyecta el workflow como secreto BUILD_ID. El último paso del despliegue hace curl a /salud hasta 10 veces y falla el run si la respuesta no contiene el SHA del commit. No hay forma de que un despliegue roto pase por bueno.

El primer despliegue crea la app y tarda varios minutos porque compila Rust en remoto. Los siguientes son mucho más rápidos.

Drive (opcional)

Drive es solo un destino de copias, nunca un origen. Se activa poniendo el id de una carpeta normal de Mi unidad en la fila «Carpeta de Drive (id)» de la sección Parámetros de CLAUDE.md. Con la fila vacía, el paso se omite sin comentarlo.

  • Solo se escribe al cerrar sesión, y solo copias de lo que ya está en el repo.
  • Solo crear o sobrescribir por nombre: nunca borrar ni renombrar.
  • Sin conversión a formato Google (disableConversionToGoogleType=true), tanto .md como .html/.png/.svg.
  • Tiene que ser una carpeta normal, no un «Proyecto» de Drive: en esos el conector no puede escribir.

Aterrizar en el PC

& ([scriptblock]::Create((irm https://raw.githubusercontent.com/npiobject/PruebaInit/main/tools/aterrizar.ps1)))

Crea %USERPROFILE%\C - Desarrollo\PruebaInit\repo con un clon de main. Es idempotente y sobrescribe sin preguntar (reset --hard + clean -fdx): la copia local es un espejo de solo lectura, no un sitio donde trabajar. Si repo\ existe con ficheros y no es un clon, el script no toca nada, lista lo que hay y termina con error.

tools\estado.ps1 responde a «¿estoy al día?» comparando el HEAD local con origin/main. Ambos aceptan -Proyecto, -Owner, -Remote, -Root y -Rama.

SíntomaCausa

init-plantilla.yml falla en «Commit y push» con without workflows permissionEl commit toca algo bajo .github/workflows/ y GITHUB_TOKEN no puede: GitHub rechaza el push entero. El workflow no debe editar ni borrar nada de esa carpeta.
Fly despliega pero la app no es tuyaEl nombre de app es único en todo Fly.io y estaba cogido; apps create lo calla con || true. Define la variable FLY_APP.
deploy.yml verde pero sin URLEs el camino «Fly no configurado». Falta el secreto FLY_API_TOKEN.
/salud devuelve otro SHAEstás mirando un despliegue anterior; comprueba el run del SHA que enviaste.
CONNECT tunnel failed, 403 en la sesiónNormal: el sandbox no alcanza Pages ni Fly. Verifica por la API de Actions.
